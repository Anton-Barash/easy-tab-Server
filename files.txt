Логика работы с файлами
1. Загрузка файла
Клиент отправляет файл на сервер вместе с метаданными (например, название, описание).

Сервер генерирует уникальный идентификатор (UUID) для файла.

Очищает оригинальное имя файла от опасных символов (оставляет только буквы, цифры, точки, дефисы, подчёркивания) — это нужно для безопасного ключа в KS3.

Формирует ключ объекта в KS3: files/{UUID}/{очищенное_имя_файла}.

Загружает файл в KS3 по этому ключу, устанавливая правильный MIME-тип (определяется по расширению или содержимому).

В базе данных создаётся запись о файле:

ID = сгенерированный UUID

Владелец = текущий пользователь

Путь в KS3 (storage_key)

Оригинальное имя файла, размер, MIME-тип, дата загрузки

Сразу же в таблицу прав добавляется запись, что владелец имеет право owner на этот файл.

Сервер возвращает клиенту ID файла (UUID) и, возможно, другую информацию.

2. Получение информации о файле
Клиент запрашивает данные файла по его UUID.

Сервер ищет запись в таблице files.

Если файл не найден — возвращает ошибку 404.

Если найден — возвращает метаданные (оригинальное имя, размер, дата, владелец и т.п.) без самого содержимого.

Проверка прав на этом этапе не обязательна, если метаданные не являются чувствительными, но можно проверять хотя бы наличие доступа.

3. Скачивание файла (получение ссылки)
Клиент запрашивает файл по UUID для скачивания (или просмотра).

Сервер проверяет, есть ли у текущего пользователя право read на этот файл. Проверка делается в таблице file_permissions:

Ищется запись, где file_id = UUID и user_id = ID текущего пользователя, и permission содержит read (или write, owner).

Если прав нет — возвращается ошибка 403.

Если права есть — сервер генерирует подписанный URL на KS3 для данного объекта. URL действует ограниченное время (например, 5–15 минут) и даёт доступ только к этому конкретному объекту.

Сервер возвращает этот URL клиенту (или делает редирект на него). Клиент скачивает файл напрямую из KS3.

Сам файл в KS3 остаётся приватным; доступ через постоянную ссылку невозможен.

4. Передача прав доступа
Владелец файла (или пользователь с правом share) может предоставить доступ другому пользователю или группе.

Запрос содержит: UUID файла, ID целевого пользователя (или группы) и тип права (read, write, share).

Сервер проверяет, что текущий пользователь имеет право share или owner на этот файл.

Если проверка пройдена — в таблицу file_permissions добавляется запись: (file_id, user_id, permission).

Если запись уже существует, право может быть обновлено.

После этого целевой пользователь получает доступ согласно выданному праву.

5. Отзыв прав
Владелец или пользователь с правом share может отозвать доступ у другого пользователя.

Запрос содержит UUID файла и ID пользователя, у которого отзывается доступ.

Сервер проверяет, что текущий пользователь имеет право управлять правами.

Если да — запись из file_permissions удаляется. Пользователь теряет доступ.

6. Удаление файла
Только владелец (или пользователь с правом owner) может удалить файл.

Запрос на удаление по UUID.

Сервер проверяет, что текущий пользователь является владельцем (сравнивает с полем owner_id в таблице files).

Если да — удаляет все записи прав для этого файла из file_permissions.

Удаляет запись из таблицы files.

Удаляет сам объект из KS3 по storage_key.

Возвращает успех.

7. Наследование прав (для папок, опционально)
Если поддерживается иерархия папок, то каждый файл может иметь parent_id (ID папки).

При проверке прав, если у файла нет прямой записи о доступе, сервер поднимается по цепочке родителей и проверяет права на папках.

Это позволяет назначать права на целую папку, и они автоматически действуют для всех вложенных файлов.

8. Публичные ссылки (опционально)
Для файлов, которые нужно сделать общедоступными, можно создать специальную публичную ссылку.

Генерируется уникальный токен, который сохраняется в отдельной таблице public_links вместе с ID файла и сроком действия.

При обращении по ссылке с этим токеном сервер находит файл, проверяет срок действия и выдаёт подписанный URL на KS3 (или редиректит).

Права на файл при этом не проверяются — доступ открыт для всех, у кого есть ссылка.

9. Резюме по структуре хранения
Все файлы хранятся в одном бакете KS3.

Ключ каждого объекта: files/{UUID}/{filename}. Это обеспечивает уникальность, отсутствие коллизий имён и упрощает администрирование.

Никакая информация о правах или владельце не закодирована в ключе — вся логика доступа лежит в базе данных.

Бакет всегда приватный; доступ через подписанные URL.

10. Безопасность
Все API-эндпоинты (кроме, возможно, публичных ссылок) защищены аутентификацией (JWT, сессии).

Подписанные URL имеют короткое время жизни.

Валидация входных данных (размер, тип файла) на сервере.

Владелец не может передать права owner другому пользователю (можно только самому себе). Права read/write/share передаются.

Администратор системы может иметь супер-доступ (отдельная роль), но это не требуется для обычной логики.
