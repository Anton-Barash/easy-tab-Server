
ТЕХНИЧЕСКОЕ ЗАДАНИЕ: ГИБКАЯ СИСТЕМА УПРАВЛЕНИЯ ДОСТУПОМ К ФАЙЛАМ ОТЧЁТОВ
=======================================================================

1. ПОСТАНОВКА ЗАДАЧИ
Приложение генерирует файлы отчётов и загружает их на сервер. Доступ к каждому файлу должен быть ограничен в соответствии с одной из трёх базовых политик:
  1) Публичный доступ – файл видят все, включая неавторизованных пользователей.
  2) Доступ для конкретных пользователей – файл доступен только явно указанным людям.
  3) Доступ для всех сотрудников компании – файл видят все участники определённой компании.

Дополнительные требования, усложняющие модель:
  - Один пользователь может одновременно быть фрилансером (работать сам на себя) и состоять в нескольких компаниях.
  - Даже внутри компании администратор должен иметь возможность запретить доступ к конкретному отчёту отдельным сотрудникам (явный запрет).
  - Система должна легко расширяться под будущие сценарии (временный доступ, права на редактирование, группы/отделы, доступ для нескольких компаний и т.д.).

Необходимо спроектировать реляционную базу данных, которая покрывает все перечисленные случаи, и описать алгоритм проверки прав доступа.

2. АНАЛИЗ ТРЕБОВАНИЙ И СЦЕНАРИИ

2.1. Базовые сценарии
  А) Публичный отчёт – любой человек, открывший ссылку на файл, получает доступ. Аутентификация не требуется.
  Б) Отчёт для конкретных лиц – владелец (или администратор) указывает список пользователей, которым разрешён просмотр. Остальные доступа не имеют.
     Пример: фрилансер создаёт личный отчёт и даёт доступ только заказчику.
  В) Отчёт для всей компании – автоматически доступен всем сотрудникам компании.
     Пример: внутренний ежемесячный отчёт компании «Ромашка» видят все её работники.

2.2. Осложняющие факторы
  - Фрилансер в нескольких компаниях: может иметь личные отчёты, состоять в компании А как штатный сотрудник и в компании Б как внешний консультант. Доступ к отчёту компании А не даёт доступ к отчётам компании Б.
  - Явный запрет для члена компании: даже если отчёт «компанейский», администратор может точечно заблокировать просмотр для конкретного человека (например, уволенного). Запрет имеет высший приоритет.
  - Создатель отчёта: по умолчанию имеет полный доступ, но компания может запретить просмотр даже автору (например, если отчёт содержит конфиденциальные данные, а сотрудник уволился). В алгоритме запрет (deny) перекрывает всё.

3. ПРЕДЛАГАЕМАЯ МОДЕЛЬ ДАННЫХ

3.1. Сущности

3.1.1. Пользователь (users)
  - id (первичный ключ)
  - name
  - email (уникальный)
  - created_at

3.1.2. Компания (companies)
  - id
  - name
  - created_at

3.1.3. Членство в компании (company_members) – связь многие-ко-многим
  - user_id, company_id (составной первичный ключ)
  - role (например: admin, member, viewer)
  - joined_at

3.1.4. Отчёт (reports)
  - id
  - title
  - file_path
  - creator_user_id (автор)
  - company_id (заполняется только для отчётов уровня 'company', опционально для 'specific')
  - access_level (ключевое поле): 'public', 'company', 'specific'
  - created_at

3.1.5. Права доступа к отчёту (report_permissions) – таблица исключений
  - id
  - report_id, user_id (уникальная пара)
  - permission_type: 'allow' (явное разрешение) или 'deny' (явный запрет)
  - granted_by (кто назначил)
  - created_at

Почему запреты хранятся здесь же? Это позволяет централизованно управлять исключениями и быстро проверять наличие запрета.

3.2. Связи между таблицами
  users ──< company_members >── companies
    │                              │
    ├── reports (creator) ─────────┘
    │        │
    └── report_permissions ────────┘

4. АЛГОРИТМ ПРОВЕРКИ ДОСТУПА (псевдокод)

def can_view(report, user):
    # 1. Публичный отчёт – доступ открыт
    if report.access_level == 'public':
        return True

    # 2. Неаутентифицированный пользователь – отказ
    if user is None:
        return False

    # 3. Явный запрет имеет абсолютный приоритет
    if report_permissions.exists(report_id=report.id, user_id=user.id, type='deny'):
        return False

    # 4. Явное разрешение – доступ открыт
    if report_permissions.exists(report_id=report.id, user_id=user.id, type='allow'):
        return True

    # 5. Базовые политики
    if report.access_level == 'company':
        return company_members.exists(user_id=user.id, company_id=report.company_id)

    if report.access_level == 'specific':
        return False   # нет ни allow, ни deny – доступ закрыт

    return False

Важные нюансы:
  - Запрет (deny) отменяет любое другое правило, включая членство в компании и авторство.
  - При уровне 'specific' без явного 'allow' доступ закрыт.

5. ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ И РАСШИРЕНИЯ
  1. Доступ на уровне отделов/групп компании – добавить таблицу company_groups.
  2. Отчёт, доступный нескольким компаниям – заменить company_id на промежуточную таблицу report_companies.
  3. Права на редактирование и удаление – расширить permission_type или добавить поле action.
  4. Временный доступ – добавить valid_from и valid_until в report_permissions.
  5. Ролевая модель администрирования – использовать company_members.role для ограничения, кто может менять политики доступа.
  6. Аудит действий – отдельная таблица логов изменений прав.

6. ЗАКЛЮЧЕНИЕ
Предложенная структура:
  - Покрывает все заявленные сценарии (публичные, групповые, персональные политики).
  - Учитывает пользователей, состоящих в нескольких компаниях.
  - Поддерживает точечные запреты (deny), важные для бизнес-процессов.
  - Легко расширяется без нарушения обратной совместимости.

ПРИЛОЖЕНИЕ: SQL-СКРИПТ ДЛЯ POSTGRESQL

-- ============================================================
-- Система управления доступом к отчётам
-- Версия: 1.0
-- СУБД: PostgreSQL 12+
-- ============================================================

BEGIN;

-- Таблица пользователей
CREATE TABLE IF NOT EXISTS users (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Таблица компаний
CREATE TABLE IF NOT EXISTS companies (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Связь пользователей с компаниями (many-to-many)
CREATE TABLE IF NOT EXISTS company_members (
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    company_id BIGINT NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
    role TEXT NOT NULL DEFAULT 'member',  -- например: admin, member, viewer
    joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, company_id)
);

-- Таблица отчётов
CREATE TABLE IF NOT EXISTS reports (
    id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    file_path TEXT NOT NULL,
    creator_user_id BIGINT NOT NULL REFERENCES users(id),
    -- company_id заполняется только для отчётов уровня 'company' (и при желании для 'specific')
    company_id BIGINT REFERENCES companies(id),
    -- Уровень доступа: public - всем, company - всем участникам компании,
    -- specific - только конкретным пользователям из report_permissions
    access_level TEXT NOT NULL CHECK (access_level IN ('public', 'company', 'specific')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Индивидуальные права (разрешения и запреты)
CREATE TABLE IF NOT EXISTS report_permissions (
    id BIGSERIAL PRIMARY KEY,
    report_id BIGINT NOT NULL REFERENCES reports(id) ON DELETE CASCADE,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    permission_type TEXT NOT NULL CHECK (permission_type IN ('allow', 'deny')),
    granted_by BIGINT REFERENCES users(id),   -- кто назначил право
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- Для одного пользователя по конкретному отчёту может быть только одно явное правило
    UNIQUE (report_id, user_id)
);

-- ============================================================
-- Индексы для ускорения проверок доступа
-- ============================================================

-- Поиск членов компании по пользователю
CREATE INDEX IF NOT EXISTS idx_company_members_user ON company_members(user_id);
-- Поиск всех сотрудников компании
CREATE INDEX IF NOT EXISTS idx_company_members_company ON company_members(company_id);

-- Поиск отчётов, принадлежащих компании
CREATE INDEX IF NOT EXISTS idx_reports_company ON reports(company_id);
-- Поиск отчётов по создателю
CREATE INDEX IF NOT EXISTS idx_reports_creator ON reports(creator_user_id);
-- Составной индекс для фильтрации по уровню доступа и компании
CREATE INDEX IF NOT EXISTS idx_reports_access_company ON reports(access_level, company_id);

-- Ускорение поиска явных прав по отчёту и пользователю
CREATE INDEX IF NOT EXISTS idx_report_permissions_report_user
    ON report_permissions(report_id, user_id);
-- Отдельный индекс для поиска запретов по пользователю
CREATE INDEX IF NOT EXISTS idx_report_permissions_user_deny
    ON report_permissions(user_id, permission_type)
    WHERE permission_type = 'deny';

-- ============================================================
-- Комментарии к таблицам
-- ============================================================

COMMENT ON TABLE users IS 'Пользователи системы';
COMMENT ON TABLE companies IS 'Компании';
COMMENT ON TABLE company_members IS 'Сотрудники компаний (роли)';
COMMENT ON TABLE reports IS 'Файлы отчётов с базовой политикой доступа';
COMMENT ON TABLE report_permissions IS 'Явные разрешения и запреты на просмотр отчётов';

COMMENT ON COLUMN reports.access_level IS '''public'' – доступен всем, ''company'' – участникам компании, ''specific'' – по белому списку';
COMMENT ON COLUMN report_permissions.permission_type IS '''allow'' – явное разрешение, ''deny'' – явный запрет (имеет приоритет)';

COMMIT;
